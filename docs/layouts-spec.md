# Layouts: requirements and per-layout design guide (Issue #20)

20 layouts in total: the 2 existing (`sidebar` → "Monolith", `timeline` → "Waypoints", ids unchanged) and 18 new ones. This file is the
single source of truth for building them. Part 1 is what every layout must do. Part 2 is the exact design brief for each new layout.

## Part 1. Rules every layout follows

### 1.1 Files you may touch (and may not)
Your layout `<id>` lives in `src/layouts/<id>/`. A placeholder already exists there: **replace it**.

* `src/layouts/<id>/<Pascal>Layout.tsx`: the component, exported with the name already imported by `registry.ts`.
* `src/layouts/<id>/<id>.css`: all of its styles (more files inside that folder are fine, e.g. a small `parts.tsx`).

**Do NOT edit anything else**: not `registry.ts`, `backend/…/catalog.py`, `shared.tsx`, `kit.tsx`, `Paginated.tsx`, `paginated.css`, `index.html`, `icons.tsx`,
other layouts, the model, the tests. They are already set up and are shared by 18 people working at the same time: a stray edit means a merge conflict.
If you need a shared change, do not make it: describe it in your report.

### 1.2 The model: zones, sections, kinds
A layout receives `{ resume }` (`Resume`: `basics`, `sections[]`, `layoutId`). Every layout declares the same three zones (already in the registry):

| zone | accepts | read with |
|---|---|---|
| `side`   | details, text, levels, links | `zoneSections(r, 'side')` |
| `main`   | text, entries                | `zoneSections(r, 'main')` |
| `header` | details, text:user (the Profile) | `<HeaderExtras resume={r} />` from `../shared` (renders them; call it **last inside your header**; style `.hx`, `.hx-text`, `.hx-p`, `.hx-facts` under your own root class) |

The three zones are the *contract with the editor*; how they are drawn is up to you. You may draw `side` sections as a column, as a band, or put
**everything in one column** (pass `side={[]}` and `main={[...sideUnits, ...mainUnits]}` to `<Paginated>`, in the order the brief says).
Section kinds and their data: `details` (facts come from `resume.basics`, use `detailRows(b)` from `../kit`), `text` (`sec.text`, Markdown, use `paragraphs(text, cls)`),
`entries` (`sec.items: Entry[]`, `sec.job` = title reads "Role at Organisation", use `entryLine`), `levels` (`name` + `level` 1-5), `links` (`label` + `url`).
**Each section renderer must handle all five kinds in either column** (one `sectionUnits(sec)` function with an exhaustive `switch`, applied to both zones), so a
user can switch layout without losing content: the editor moves sections between zones, never drops them.
Entry fields: `title, organisation, location, start, end, current, note (bold highlight line), description (Markdown), bullets[]` (a bullet starting with `#` is a subheading;
`bodyPieces`/`entryPieces` in `../kit` handle it). Dates: `entryDates(en)` from `../../model/dates`. Headline is `basics.headline`; name `basics.firstName` / `lastName`;
`fullName(b)`, `locationLine(b)`, `addressLines(b)` are in `../../model/format`.

Use the building blocks in `src/layouts/kit.tsx` (`bodyPieces`, `entryPieces`, `withHeading`, `detailRows`, `levelPct`) and `shared.tsx` (`Rich`, `paragraphs`, `parseBullets`, `entryLine`,
`HeaderExtras`). Read `src/layouts/sidebar/` and `src/layouts/timeline/` first: they are the reference implementations. Class names: **every class starts with `lx-<id>`**
(e.g. `lx-terminal-title`), the root is `<Paginated className="lx-<id>" …>`, and every CSS rule is scoped under `.lx-<id>` (set CSS variables on `.pg.lx-<id>`).

### 1.3 Paging (A4) and printing
* Content is a list of `Unit`s per column; the paginator fills pages greedily and never splits a unit. So **one unit = the largest thing that may not break** (a heading + first piece, one bullet…); long entries must be several units (use `entryPieces`). A section title must travel with its first unit (`withHeading`). A unit must never be taller than a page.
* Page geometry is set by CSS variables on your root (defaults in `paginated.css`): `--pad-t --pad-x --pad-b --side-w --side-pr --main-pl --main-rule --col-pad --col-pad-rest`. You may also override `.lx-<id> .pg-body { grid-template-columns: … }` (e.g. a right-hand side column: `1fr var(--side-w)` plus `.pg-side { order: 2 }`), `.pg-page` background, etc. Keep the page 210×297 mm.
* The header appears on page 1 only. Continuation pages (`.pg-cont`) must look finished too: page background, column rules and bands must persist; first-line spacing is `--col-pad-rest`.
* Page-wide colour (dark pages, tinted columns, grids) goes on `.lx-<id> .pg-page` (`background`, `background-image: linear-gradient(...)`): it is repeated on every page. A full-bleed header band: negative margins on `.pg-header` equal to the page padding (`margin: calc(-1 * var(--pad-t)) calc(-1 * var(--pad-x)) 0`); `.pg-page` clips overflow.
* No fixed heights tied to content, no `position: fixed`, no scripts, no `vh/vw` units, nothing that depends on the viewport. Decorations are CSS or inline SVG only. Absolutely-positioned decoration is fine inside a `position: relative` box that has its own in-flow height.
* **Print / PDF**: `print-color-adjust: exact` is already inherited from `.pg`, so backgrounds print. Still: draw every rule, bar, dot and fill that carries meaning as an element with a `background` colour (not `border`, not SVG strokes alone) so the print check can see it. **Page 1 of the sample CV must paint at least one coloured background** (a rule drawn as a 0.25 mm-high `background` div counts). No `mix-blend-mode`, `filter`, `backdrop-filter`, `text-shadow`, or `opacity` on large areas (they print differently); use solid colours (rgba is fine on small decoration).
* The layout is also rendered as a small thumbnail (≈ 1/4 scale) on the "My CVs" page and in the "Start from a layout" gallery: name, headline and section headings must be legible and the page's colour identity obvious at that size.

### 1.4 Content robustness (all five must look right)
1. **Sample CV** (`/lab/<id>`): the Jane Doe CV, all sections placed by default (details/skills/languages/links/hobbies in `side`; profile/employment/education/courses/achievements in `main`).
2. **Empty CV** (`?data=empty`): no name, no content. Must not crash, must not print stray headings, empty boxes, orphan rules or lone punctuation (e.g. a JSON `{` with nothing inside is fine, a "$ cat" with no output is not). A section with no content renders nothing; `details` with no facts renders nothing.
3. **Long CV** (`?data=long`): 3-4 pages. No clipped text, no heading stranded at a page bottom, no overlap, balanced columns, decoration consistent on every page.
4. A section moved to the other zone (e.g. skills into `main`, profile into `side`) still renders sensibly.
5. Long words / URLs / long titles wrap (use `overflow-wrap: anywhere` where a column is narrow). Names that are very long or very short.
Also: with `icons: true` in the registry the editor offers an icon per section: draw `SECTION_ICONS[sec.icon]` (from `../icons`) where the brief says, skip it when `sec.icon === 'none'`, and the heading must still look intentional without it. With `icons` unset, do not draw icons.

### 1.5 Typography
* Only fonts from this list are loaded (Google Fonts, already in `index.html`, allowed by the CSP). **No new fonts, no `@import`, no `url(http…)`, no external images, no new network request of any kind.** Always give a fallback stack (`'Inter', system-ui, sans-serif`; `ui-monospace, monospace` for mono; `Georgia, serif`).
  Montserrat 400-700 · Oswald 300-500 · Source Sans 3 400/600/700 · JetBrains Mono 400/500/700 · IBM Plex Mono 400/500/600 · IBM Plex Sans 400/500/600 · Space Mono 400/700 · Barlow Condensed 500/600 · DM Sans 400/500/700 · Roboto Condensed 400/700 · Roboto Mono 400/500 · Fira Code 400/500 · Inter 400/500/700/900 · Fraunces 300/600 + italic 400 · Work Sans 400/500/600 · Playfair Display 700/900 + italic 400 · Libre Franklin 400/600 · Archivo Black · Archivo 400/600 · Nunito Sans 400/600/700 · Nunito 700/800 · Quicksand 500/700 · Cormorant Garamond 500/600 + italic 500 · Jost 400/500 · EB Garamond 400/500/600 + italic 400 · Space Grotesk 400/500/700 · Instrument Serif 400 + italic · Bricolage Grotesque 400/600/800.
  Use only the weights/styles listed for a family (anything else is synthesised and looks wrong). Don't use italic of a family with no italic listed.
* Sizes in `pt` (this is a printed page): body 8.8-10.5 pt, never below 8 pt for running text and 7.2 pt for tiny uppercase labels. Line-height 1.3-1.5 for body. Name ≥ 22 pt. Use `mm` for spacing.
* Markdown in descriptions/bullets/notes renders through `Rich`/`paragraphs`; style `strong`, `em`, `a`, `code` and tables (`.md` class) under your root so they match.

### 1.6 Colour and contrast (WCAG AA, on screen and printed)
Body text ≥ 4.5:1 against the colour *directly behind it*; secondary/meta text ≥ 4.5:1 too (no pale grey dates); large text (≥ 18 pt or ≥ 14 pt bold) and non-text marks that carry meaning (bars, markers) ≥ 3:1. Compute it, do not eyeball it: a tiny script
(`node -e` or python) with the WCAG luminance formula is enough. Dark-page layouts are on purpose (the print path forces backgrounds on). Colour must never be the only signal: a level bar is also readable from its filled length, a "current" entry is also labelled "Present".
Link text must be distinguishable from body text (underline or colour + underline).

### 1.7 Accessibility and semantics
Real headings (`<h1>` name, `<h2>` section titles, `<h3>` entry titles where natural), lists as `<ul><li>`, links as `<a href>`. Decorative elements `aria-hidden`. Don't put essential text in `::before`/`::after` (except punctuation, bullets, quotes and the like).

## Part 2. The 18 new layouts

### 1. `document` · "JSON Document" · technical (backend, platform, API) · `DocumentLayout`
**Idea:** the CV *is* a JSON file open in an editor. **Page:** white `#ffffff`, margins 14 mm. **One column** (all units in `main`; order: header, then side sections, then main sections).
**Font:** JetBrains Mono 400/500/700, 8.4 pt / 1.5, everything monospace; keys 500.
**Syntax colours (light theme, all ≥ 4.5:1 on white):** keys `#0451a5`, strings `#a31515`, numbers `#098658`, booleans/null `#0000ff`, punctuation `#383a42`, comments/meta `#6a737d`.
**Header (replaces the name block):** a slim "tab" strip `#f3f4f6`, 7 mm high, with a small blue dot and the file name `jane-doe.cv.json` (slug of the name; `untitled.cv.json` when empty) in 7.4 pt `#6a737d`, hairline under it. Then the document opens: `{`, `"name": "Jane Doe",` `"headline": "…",` then contact keys (`"email"`, `"phone"`, `"location"`) when filled, then `HeaderExtras` as a nested `"summary"` string/object. Name value in bold 11 pt so the name reads as the title even at thumbnail size.
**Structure:** every section is a key (title → lowerCamelCase: "Employment History" → `"employmentHistory"`): `text` → a string value (paragraph(s) in the string colour, wrapped in quotes, continuation lines indented); `entries` → an array of objects (`"title"`, `"organisation"`, `"location"`, `"start": "2022-01"` (string), `"end": null` or string, `"current": true` (boolean colour), `"note"`, `"description"`, `"bullets": [ "…", "…" ]`; omit empty keys; `Rich` markdown inside strings is allowed); `levels` → an object map `"TypeScript": 5` (number colour); `links` → object map `"LinkedIn": "https://…"` (links clickable); `details` → nested object of the filled facts. Indentation by nesting: 2 characters per level (use `ch`), with faint dotted indent guides (`#e5e7eb`) painted as backgrounds. Commas after every value except the last of its container; closing `}` / `]` on their own line; the very last unit closes the root `}`. Empty CV: just `{` `}` with a `// empty` comment, nothing else.
**Gutter:** a 9 mm left gutter with chevrons `▾` in `#9ca3af` on lines that open a block (decorative, `aria-hidden`); no line numbers (they cannot be kept right across pages).
**Signature:** a `// comment` line in `#6a737d` before each section (its title), so headings still scan; the entry's `"title"` value is 600/bold so entries are findable.
